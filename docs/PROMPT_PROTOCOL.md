# Prompt and result protocol

The request ZIP uses the same reading-quality and privacy rules across ChatGPT and other AI services. The result must include a complete, schema-compatible `result.json`, a substantial `report.md`, and a `manifest.json`. When the environment provides image generation, generating exactly one detailed individualized card is mandatory after the reading and JSON schema validation. In ChatGPT, call gpt-image. Do not stop at writing an image prompt or silently omit the image when generation is available. If the image tool is unavailable, access/quota is missing, or the generation call fails, finish the reading and ZIP without an image and record the actual status.

Prefer 1200×675 (16:9), but accept and package the returned raster at its actual dimensions. A size mismatch never invalidates the result, triggers a retry, or stops ZIP creation. Preserve the actual PNG, JPEG, WebP, or GIF extension. Never substitute SVG, HTML/CSS, Canvas, Python, programmatic drawings, templates, or existing art for generated art. Only list files that actually exist in `manifest.files`.

The generated image is one finished, detailed Japanese fortune infographic, inspired by the supplied references: deep indigo night sky, intricate gold framing, readable parchment panels, a central painted symbolic scene derived from the actual reading, and multiple clearly organized information panels. Include an anonymous overall conclusion, personality portrait, three strengths, two or three cautions, three practical pieces of advice, key answers to the user's questions, and actual calculated evidence. Use only sections supported by the final reading. Do not invent scores, percentages, timelines, dates, charts, placements, or other claims. Keep Japanese text readable and use the exact claims in `assets.shareCardCopy.sections` or `report.md`; do not create a sparse title-only poster. No post-generation CSS/Canvas text overlay.

Never put a real name, reading, alias, birth date/time, birthplace, current location, age, gender, contact details, or other identifying profile facts in the card image, card copy, or card-generation metadata. Visual motifs must trace to actual non-identifying facts in the calculation. Store anonymous `title`, `description`, `themes`, structured `sections`, and fact-linked `visualMotifs` in `assets.shareCardCopy`, even if image generation fails. When generated, set `assets.shareImage` to the real path and include it in the ZIP and manifest. Record the actual provider, model, tool, and known dimensions in `assets.shareGeneration`; never claim a tool that was not used. Without an image, omit `assets.shareImage` and set status to `unavailable` or `failed`. The no-image result remains valid.

The core result ZIP contains `result.json`, `report.md`, and `manifest.json`; the card is included whenever generation succeeds. If a service cannot return ZIP attachments, return one self-contained `result.json` containing the full narrative in `reportMarkdown`. The copy-prompt flow instead returns the reading and, when image generation is available, the same required detailed card directly in chat; it does not ask for JSON or ZIP.

All system collections, including `calculations`, are arrays. Preserve the Draft 2020-12 schema. The app accepts older version 1.0.0 archives, missing images, alternate image dimensions, nested ZIP folders, and common object-shaped list fields; importer repairs are reported as notices.

When a birth time is missing, mark only time-dependent components unavailable. Use a partial status and include reliable date/place-based calculations that remain possible. If a system truly cannot be calculated, keep its section in both JSON and report, explain why it is on hold, which input is missing, and what that input would unlock; do not leave an unexplained empty object or replace it with generic tradition text. For Jyotish, Nakshatra, and Dasha, distinguish date-based elements from Lagna/houses, boundary-sensitive lunar placement, and dasha start degrees that depend on time. Never invent placements.
