# Prompt and result protocol

The request ZIP shares the same reading quality and privacy rules across ChatGPT and other AI services. The result must always include a complete, schema-compatible `result.json`, a substantial `report.md`, and a `manifest.json`. Image creation is a best-effort extra: try one native image-generation call after finishing and validating the reading, but do not let tool availability, timeouts, unsupported dimensions, or image failures stop the report or result ZIP.

When available, prefer ChatGPT's gpt-image. Other services may use their own native image generator and must record the actual provider, model, tool, and known dimensions; never claim a tool that was not used. The preferred card size is 1200×675 (16:9), but use and include the returned raster image as-is if the service only supports another size. PNG, JPEG, and WebP are accepted. Never substitute SVG, HTML/CSS, Canvas, Python, programmatic drawings, or an existing image for generated art. If no image is generated, omit `assets.shareImage`, record an optional `shareGeneration.status` of `unavailable` or `failed`, and finish the ZIP with no image. Image generation is not a schema or ZIP requirement.

Only list files that actually exist in `manifest.files`. The core result ZIP has `result.json`, `report.md`, and `manifest.json`; `assets/share.*` is optional. If a service cannot attach a ZIP, return one self-contained `result.json` with the full narrative in `reportMarkdown`; the app accepts standalone result JSON files. The copy-prompt flow instead returns the reading directly in chat and attempts an image only when available.

All system collections, including `calculations`, are arrays. Preserve the Draft 2020-12 schema for the rest of the result. The app also repairs common object-versus-array and root-folder packaging variations with an import notice. Existing version 1.0.0 archives with the earlier required `assets/share.png`, `shareCardCopy`, and `shareGeneration` fields remain supported.

No card may include a name, reading, alias, birth date/time, birthplace/current location, gender, contact details, or other identifying profile facts. The report cover is a fixed CSS design in landscape 3:2 and is not generated.

When a birth time is missing, mark only time-dependent components unavailable. Use a partial status and include reliable date/place-based calculations that remain possible. If a system truly cannot be calculated, keep its section in both JSON and report, explain why it is on hold, which input is missing, and what that input would unlock; do not leave an unexplained empty object or replace it with generic tradition text. For Jyotish, Nakshatra, and Dasha, distinguish date-based elements from Lagna/houses, boundary-sensitive lunar placement, and dasha start degrees that depend on time. Never invent placements.
